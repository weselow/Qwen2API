# Прод-деплой гибридного конвейера v2 (jik.5)

`docker/docker-compose.prod.yml` — рабочий прод-стек: Qwen2API (debian-образ с
`curl-impersonate-chrome` из jik.2) + sidecar `signin-worker` (jik.3) + sidecar
`dnsproxy`. Это объединение `docker-compose.dns.yml` и `docker-compose.signin.yml`;
те остаются самостоятельными dev-вариантами. Обоснование архитектуры —
`docs/hybrid-v2-pipeline-design.md`, живые доказательства —
`docs/et0-live-integration-2026-11-21.md`.

В этом же стеке живёт **browser egress** (эпик Qwen2API-3ue): рабочие запросы к
qwen.ai умеют уходить изнутри открытой страницы Chromium воркера — единственного
транспорта, который qwen.ai пропускает с IP прода с 23.11. Он выключен по
умолчанию и включается флагами; на 24.11 включать рано — живой смоук не пройден
(Qwen2API-3ue.5). Как его выкатывать, наблюдать и откатывать — в конце документа:
«Browser egress: эксплуатация» и «Выкатка browser egress».
Дизайн и контракты — `docs/browser-egress-design.md`.

## Отличия от DNS-стека

- Образ приложения пересобирается из debian-базы (glibc): в `/usr/local/bin`
  лежит `curl-impersonate-chrome` v0.6.1; `COMPLETIONS_TRANSPORT=auto` находит
  его по PATH и гоняет completions через Chrome ClientHello + HTTP/2.
- `signin-worker` (node:20-slim + Playwright + Chromium) получает и тихо
  продлевает сессии chat.qwen.ai; профили Chromium — в volume `signin_profiles`
  (внутри живые сессии: защищать как данные аккаунтов). Портов наружу нет.
- `signin-worker` тоже резолвит qwen.ai через DoH-sidecar (`dns:` + сеть
  `dns_sidecar`), как и приложение.
- Приложение стартует только после healthy у `dnsproxy` и `signin-worker`.

## Переменные

Полный пример — `docker/prod.env.example`. Сверх DNS-стека:

| Переменная | Назначение |
| --- | --- |
| `V2_SESSION_MODE` | `browser` (дефолт этого Compose) — сессии из sidecar; `off` — v1-путь |
| `COMPLETIONS_TRANSPORT` | `auto` (дефолт): impersonate, если бинаррь есть, иначе axios; `axios` — принудительно v1-транспорт; `browser` — completions стримятся из резидентной страницы signin-worker (Qwen2API-3ue.3, `docs/browser-egress-design.md`); включать только явно, после `CHAT_CREATION_TRANSPORT=browser` |
| `CHAT_CREATION_TRANSPORT` | `direct` (дефолт Compose, Qwen2API-3ue.2): `chats/new` из Node, как раньше. `browser` — изнутри резидентной страницы воркера (`/egress`); включать явно, одной пробой. Подробности и откат — `docs/browser-egress-design.md` |
| `SIGNIN_WORKER_TOKEN` | Общий bearer приложение → воркер; пусто = без авторизации (только внутренняя сеть) |
| `SIGNIN_PROFILES_DIR` | Каталог профилей Chromium; по умолчанию named volume `signin_profiles` |
| `SIGNIN_HEADLESS_MODE` | Воркер: какой headless-браузер открывает страницы — `shell` (по умолчанию, как раньше) или `chrome` (полный Chromium, предъявляется как браузер с окном). Рычаг на случай, если qwen.ai откажет headless-странице; см. «Headless-страница и `SIGNIN_HEADLESS_MODE`» |
| `MAX_RESIDENT_PAGES` | Воркер: лимит открытых страниц одновременно, по умолчанию `16`; см. «Резидентные страницы» |
| `SIGNIN_FORGET_DELETES_PROFILE` | Воркер: удалять ли профиль браузера вместе с аккаунтом, когда его удаляют в приложении (`POST /forget`, Qwen2API-2l0). По умолчанию `false` — профиль остаётся, и добавленный заново аккаунт пропускает вход; `true` — cookies удалённого аккаунта уходят вместе с профилем. Включает только точное `true`. Решение за владельцем; см. «Запрос в полёте через удалённый аккаунт» в `docs/signin-worker.md` |
| `SIGNIN_FORGET_GRACE_MS` | Воркер: пауза перед удалением профиля удалённого аккаунта, по умолчанию `120000` (2 минуты): аккаунт, добавленный заново внутри паузы, сохраняет профиль и пропускает вход по паролю (Qwen2API-t8s); `0` — удалять сразу. Действует при `SIGNIN_FORGET_DELETES_PROFILE=true`; см. «Переменные воркера» в `docs/signin-worker.md` |

**Флаги новых переменных в Coolify (Qwen2API-9x1).** Coolify 4.7.6 заводит
переменную, которую деплой впервые встретил в compose-файле, с флагом «Build
time» (`is_buildtime=true`); тот же флаг ставит `POST /api/v1/applications/<uuid>/envs`
без явного `is_buildtime`. Заполненная build-time переменная при каждой смене
значения стоит полной пересборки с загрузкой Chromium. Поэтому **после каждого
деплоя, добавившего переменные в compose, проверять флаги production-переменных
и снимать build time у новых**: со build time остаются только
`SERVICE_URL_QWEN2API` и `SERVICE_FQDN_QWEN2API` — они постоянные, их не трогать.

```sh
# $CT — токен API из приватного connections.md, $CB — адрес API Coolify (…/api/v1),
# <uuid> — ресурс приложения
curl -s -H "Authorization: Bearer $CT" "$CB/applications/<uuid>/envs" \
  | jq -r '.[] | select(.is_preview == false and .is_buildtime == true) | "\(.key) buildtime=\(.is_buildtime | tostring) runtime=\(.is_runtime | tostring)"'
# всё, кроме двух SERVICE_*, — runtime-only. Снять флаг по существующей переменной
# (значение можно не слать) — Coolify отвечает 201:
curl -s -o /dev/null -w '%{http_code}\n' -X PATCH -H "Authorization: Bearer $CT" -H 'Content-Type: application/json' \
  "$CB/applications/<uuid>/envs" \
  -d '{"key":"<KEY>","is_preview":false,"is_runtime":true,"is_buildtime":false}'
```

Флаг читать как `(.is_buildtime | tostring)`: запись `.is_buildtime // "null"`
печатает `null` и для `false`. Preview-записей (`is_preview=true`) это не
касается. После снятия — перечитать список тем же `GET`: у переменной
`buildtime=false runtime=true`.

Вторая копия стека на том же хосте (превью/тест) обязана взять **другую**
`DNS_SUBNET` + `DNS_SIDECAR_IP`: dnsproxy пинит статический IP в своей сети.

## Coolify: перевод существующего ресурса

Меняется существующий ресурс (хранилища и домен сохраняются), по аналогии с
`docs/dns-sidecar.md`:

1. Base Directory `/`, Compose Location `/docker/docker-compose.prod.yml`,
   ветка прежняя (`production`). Не принимать «Use /docker as base directory».
2. В Environment Variables добавить `SIGNIN_WORKER_TOKEN` (случайный секрет);
   при необходимости `V2_SESSION_MODE`/`COMPLETIONS_TRANSPORT` (дефолты уже
   browser/auto). Остальные переменные без изменений.
3. Persistent Storage прежние (`./data`, `./logs`, `./caches` того же ресурса).
4. Домен/маршрутизация — на сервис `qwen2api`, порт 3000, как раньше; для
   `signin-worker` и `dnsproxy` домены и port mapping не создавать.
5. Deploy без Stop: Coolify собирает образы при живых старых контейнерах, затем
   снимает старые и поднимает новые — двух dnsproxy в подсети не бывает (порядок
   виден в логах деплоя; проверено 25.11).

## Живой смоук из контейнера (jik.5)

Полный цикл проверяется из контейнера приложения (его egress и есть прод).
В runtime-образе нет утилитного curl — HTTP из контейнера удобнее гонять
через bun; impersonate-бинаррь проверяется напрямую:

```sh
docker exec <qwen2api-контейнер> /usr/local/bin/curl-impersonate-chrome --version
# health sidecar изнутри приложения
docker exec <qwen2api-контейнер> bun -e 'fetch("http://signin-worker:3100/health").then(async r=>console.log(r.status,await r.text()))'
# 1) signin: аккаунт без токена → browser-вход через воркер (creds через env, не argv)
docker exec -e SMK=<API_KEY> -e EM=<email> -e PW=<password> <qwen2api-контейнер> \
  bun -e 'fetch("http://127.0.0.1:3000/api/setAccount",{method:"POST",headers:{Authorization:"Bearer "+process.env.SMK,"Content-Type":"application/json"},body:JSON.stringify({email:process.env.EM,password:process.env.PW})}).then(async r=>console.log(r.status,await r.text()))'
# 2) chats/new + completions + ответ модели одним вызовом
docker exec -e SMK=<API_KEY> <qwen2api-контейнер> \
  bun -e 'fetch("http://127.0.0.1:3000/v1/chat/completions",{method:"POST",headers:{Authorization:"Bearer "+process.env.SMK,"Content-Type":"application/json"},body:JSON.stringify({model:"qwen3.7-plus",stream:true,messages:[{role:"user",content:"Say pong"}]})}).then(async r=>console.log(r.status,(await r.text()).slice(-300)))'
# логи конвейера
docker logs --since 15m <qwen2api-контейнер> 2>&1 | grep -E "\[(ERROR|AUTH|CHAT|ACCOUNT|V2SESSION)\]" -A1
```

Ожидание: `setAccount` отдаёт 200 (воркер прошёл форму + капча Aliyun прошла
сама), completions стримит ответ модели. Если на impersonated-TLS ловится
`FAIL_SYS_USER_VALIDATE`/`RGV587_ERROR` (Baxia punish) — это ожидаемый риск
датацентрового egress-IP (см. Risks в дизайн-доке): поведение Baxia с
датацентрового IP отличается от домашнего; митигируется пер-аккаунтными
прокси (`account.proxy` передаётся и в воркер, и в curl).

## Откат

Одним конфигом, без перекодирования: `V2_SESSION_MODE=off` +
`COMPLETIONS_TRANSPORT=axios` в env ресурса → Deploy без Stop (переменные стека
runtime-only: пересборки нет). Приложение
возвращается к v1-поведению (axios, логин по v1-пути), sidecar'ы остаются и
останавливаются независимо. `V2_SESSION_MODE=off` без `COMPLETIONS_TRANSPORT`
тоже валиден: auto продолжит ездить через impersonate — это не v1-транспорт,
поэтому для полного отката нужны обе переменные.

## Результат смоука 2026-11-21

Стек `docker/docker-compose.prod.yml` поднят на прод-хосте Coolify
(10.20.0.210) как изолированный превью-проект `qwen-hybrid-smoke`: отдельная
подсеть `172.30.54.0/24`, порт только `127.0.0.1:23216`, свои data/logs/caches.
Тот же docker-демон и тот же egress-IP, что у прода; creds тестовой учётки
передавались через env в `docker exec`, в логи не попали.

**Найдено и починено по дороге (именно то, ради чего нужен живой смоук):**

1. Образ воркера ставил Chromium от root в `/root/.cache/ms-playwright`, а
   рантайм идёт от `USER app` (uid 10001) и браузера не находил → фиксированный
   `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` + `a+rX`.
2. В runtime-образе не было CA-бандла для curl (`curl: (77) error setting
   certificate verify locations`) — bun несёт свой стор, а curl-impersonate
   нужен `/etc/ssl/certs/ca-certificates.crt` → `ca-certificates` в стейдже.
3. `readStableToken` умирал на пост-логинной навигации FE
   (`page.evaluate: Execution context was destroyed`) → destroyed-context
   читается как «токен ещё не устоялся», ретрай на следующем документе.

**Полный цикл из контейнера — работает (датацентровый egress):**

- `GET /v1/models` → 200, живой каталог qwen.ai (22 КБ, `qwen3.7-plus`).
- Signin (browser): `POST /session` у воркера → 200, JWT + 19 cookies включая
  HttpOnly `refresh_token`; капча Aliyun прошла сама из контейнера. Первый
  прогон (форма+капча) занял ~20 с, повторный по живому профилю — 3.4 с.
- `POST /api/setAccount` → 200 «аккаунт создан», воркер отдал сессию в jar
  адаптера.
- `POST /v1/chat/completions` (stream) → **200 `text/event-stream`**, ответ
  модели «pong», usage от upstream (1205/110). Подтверждено трижды.
- Персистентность jik.4 вживую: после пересоздания контейнера приложение
  поднялось с «v2 сессий восстановлено: 1 действительна» без нового входа.

**Baxia и датацентровый IP.** На impersonated-TLS ни одного punish за весь
смоук. Отдельно зафиксировано: в откат-режиме (`COMPLETIONS_TRANSPORT=axios`,
plain Node TLS) completions с этого egress тоже прошли (200, единичная
проба) — с домашнего IP axios карался стабильно. Вывод: риск-скор этого
датацентрового egress сейчас не хуже домашнего, но однопробное наблюдение —
не гарантия: impersonate остаётся дефолтом, пер-аккаунтные прокси — рычаг
при деградации скоринга.

**Откат конфигом проверен:** `V2_SESSION_MODE=off` + `COMPLETIONS_TRANSPORT=axios`
(только env, без перекодирования) → приложение стартует без v2-restore в
логе, воркер не получает ни одного запроса, completions идут через axios и
обслуживаются 200; возврат `browser`/`auto` восстанавливает гибрид (200
«pong» на следующем же запросе).

## Первый боевой деплой 2026-11-21 (Coolify, ветка production, efd204d)

Переключение выполнено через Coolify API (compose location →
`/docker/docker-compose.prod.yml`, env `SIGNIN_WORKER_TOKEN`), Stop → Deploy,
все три контейнера healthy. Миграция аккаунтов на v2-сессии:

1. **Бутстрап-окно.** Аккаунты с непротухшими v1-токенами не логинятся сами
   (токен «валиден», v2-сессии нет) — completions падали 409
   `v2_session_required` до первого тика авто-refresh (≤15 мин). Лечение:
   последовательный `POST /api/refreshAccount` по каждому аккаунту
   (браузерный вход ~17–20 с на аккаунт, капча проходила сама).
2. **Ротация при сходе.** Вход даёт короткий токен (~15–30 мин); тёплый
   таймер воркера перезагружает профиль и ротирует токен на ~30-дневный.
   Пока приложение держит короткий токен, первый 401 → инвалидация →
   продление из кэша воркера — одноразовый само-лечащийся хикап на аккаунт.
   Ускорение сходимости: второй проход `refreshAccount` (отдаётся из кэша
   воркера мгновенно, без браузера).
3. **Baxia риск-скор egress-IP — ГЛАВНЫЙ УРОК.** До серии входов тот же IP
   весь смоук отработал чисто (включая однопробный axios на chats/new).
   После 9 браузерных входов за 3 минуты + диагностических проб скор
   эскалировал: completions punish («被挤爆啦»), затем chats/new стал отдавать
   слайдер-страницу вместо JSON на plain-Node TLS, затем жёсткий 405-блок
   даже на curl-impersonate. Т.е. блокируется IP целиком, не TLS-отпечаток:
   длина ноги impersonate не спасает, когда скор IP уже поднят. Рычаг из
   дизайн-дока — **пер-аккаунтные прокси** (`account.proxy` проходит и в
   браузерный контекст, и в curl); альтернатива — остывание скора (типично
   минуты-часы) и мягкое перезакрепление аккаунтов (без пачковых входов).
   Диагностические пробы с самого egress кормят скор — минимизируйте их.

## Инцидент 2026-11-23: IP прода не пропускает запросы не из браузера

**Что случилось.** На проде (тот же стек, код af2e706, `V2_SESSION_MODE=browser`,
`COMPLETIONS_TRANSPORT=auto`) аккаунт добавлен в 12:48, и с 12:50 каждая
генерация падала с `502 upstream_session_unauthorized` (92 из 92). Сервис был
поднят, аккаунт был жив.

**Разбор — по одной пробе, 23.11:**

- Настоящий Chromium из профиля воркера, с того же IP: `POST /api/v2/chats/new`
  → `success:true`. Аккаунт и IP живы для браузера.
- Тот же вызов из Node (axios): `unauthorized`, каждый раз.
- curl-impersonate-chrome с полной банкой cookies: жёсткий `405` (страница
  блокировки Baxia). Блок для «не-браузерных» запросов с этого IP, поднятый 21.11,
  держался; двое суток остывания не помогли.
- «Тихое продление» было пустым: воркер отдавал кэш, пока токен не истёк, и цикл
  «отказали → продлили» крутил одну и ту же банку cookies от 12:48.

**Что это значит.** Блок адресный: с этого IP пропускают только то, что похоже на
браузер. Смена TLS-библиотеки не лечит (impersonate отклонён), откат конфигом —
тоже: axios и curl-impersonate остаются запросами не из браузера.

**Что сделано.** Эпик Qwen2API-3ue: рабочие вызовы (`chats/new` и completions)
умеют уходить изнутри открытой страницы Chromium воркера, где qwen.ai видит
его собственный TLS и его живые cookies. Как это включить — ниже.

**Уроки** (в дополнение к 21.11):

- Пачка входов и диагностических проб с одного IP поднимает скор так, что он не
  спадает днями. Диагностика — по одной пробе и с паузой.
- Первой идёт проба, которая разделяет «IP заблокирован» и «сессия умерла»:
  браузер против Node с одного и того же IP. Здесь она сразу показала, что
  лечится только транспортом.
- Дешёвое «продление», которое ничего не делает, маскирует отказ: цикл ошибок
  выглядит как восстановление.

### Что включается

| Переменная | Выключено (по умолчанию в Compose) | Включено |
| --- | --- | --- |
| `CHAT_CREATION_TRANSPORT` | `direct` — `chats/new` из Node, как раньше | `browser` — изнутри страницы воркера |
| `COMPLETIONS_TRANSPORT` | `auto` — curl-impersonate, иначе axios | `browser` — изнутри той же страницы, ответ стримится |
| `SIGNIN_HEADLESS_MODE` | `shell` | `chrome` — если qwen.ai отказал headless-странице |

Два правила, из-за которых легко ошибиться:

- **`CHAT_CREATION_TRANSPORT=auto` в прод-окружении означает «включено»** (это
  `browser`, когда `V2_SESSION_MODE=browser` и задан `SIGNIN_WORKER_URL`). Для
  выкатки с выключенными флагами — не задавать.
- Воркер и приложение обновляются вместе: они один стек, так и выходит. Старый
  воркер с новым приложением ломает и продление (не знает `force`), и стриминг
  (не знает `stream`).

С Qwen2API-03v (на проде с 25.11 20:47 UTC, образ `ff8e6a7`) те же два флага
уводят через страницу и остальное: `COMPLETIONS_TRANSPORT=browser` — генерацию
картинок и видео, `CHAT_CREATION_TRANSPORT` — информацию о чате, статус
видеозадачи, STS-токен (с 26.11 — у адреса страницы, `/api/v2/files/getstsToken`)
и разбор файла. Напрямую из Node остаются скачивание результата с CDN и заливка
байтов в OSS — это не qwen.ai (CDN результата с адреса прода доступен: 25.11,
`200`, `video/mp4` за 0,9 с; заливка в OSS напрямую проверена живьём 26.11 —
подписью V4, с регионом из ответа). Как устроено — `docs/signin-worker.md`,
«Картинки/видео и файлы через воркер». Тишина qwen.ai на опросе (статус видеозадачи, информация
о чате) стоит пропущенного опроса — двух подряд, не больше; в логе приложения
это `опрос пропущен: qwen.ai молчит через страницу (<код>), N из 2 подряд`, а
третий подряд — `… — запрос завершается отказом` и клиенту `503` (клиенту
`stream: true` у видео, чей keep-alive уже начал поток, — кадр ошибки в нём).
Это не страница-проверка и не перезагрузка страницы: `renew` и `session` в логе
воркера при этом не появляется. Строки уровня error при пропуске пишутся те же,
что и при фатальном отказе (`获取聊天详情失败`, `查询视频任务状态失败`) —
пропуск отличает только предупреждение рядом. Запрос видео из-за пропусков
может идти дольше: если qwen.ai отвечает лишь на каждый третий опрос — около
40 минут на одного кандидата задачи.

Чего выкатка **не** чинит (заведено отдельно): уход клиента не останавливал
генерацию в текстовых потоковых путях (Qwen2API-mxs) — с Qwen2API-mxs закрыто,
см. ниже; уход клиента в путях картинок/видео и CLI закрыт 26.11
(Qwen2API-3ue.10; код в main, на проде — с выкатки этой пачки; живьём не
проверено — «Уход клиента», конец раздела). Файл в промпте
она больше не ломает. До 26.11 qwen.ai отвечала `405` HTML-страницей ошибки на
первый файловый вызов из страницы, `POST /api/v1/files/getstsToken`: клиент с
`tools` получал `503 upstream_unavailable` («Upstream document parse unavailable;
retry shortly»), без `tools` — ответ без документа (контекст урезан, в логе «Agent
上下文附件失败，已保留最近上下文»). Причина была в адресе: страница просит токен у
`/api/v2/files/getstsToken`, и по этому адресу вызов из страницы проходит
(Qwen2API-3ue.12; `docs/browser-egress-design.md`, «STS-токен: адрес и форма
страницы»).

### Какой аккаунт взял запрос

В логах воркера адресов нет — узнать аккаунт запроса по ним нельзя. Два способа:

- **Счётчики расхода** — `GET /api/accountStats` приложения: у аккаунта, взявшего
  запрос, выросли `chat.input` и `chat.output`; счётчики переживают перезапуск
  приложения. На хосте — `bash /root/v2-acc.sh state` (рядом — запись ротатора и
  кто следующий). На картинке и видео счётчики не растут (27.11) — аккаунт таких
  запросов по ним не узнать.
- **Число открытых страниц** — `(N/M pages)` в строках воркера: второй аккаунт
  в том же запросе открыл бы вторую страницу.
- **Адрес в логе приложения** — строка `v2 会话已续期` называет аккаунт, но только
  у перезагрузки после отказа; у обычного запроса адреса нет нигде.

Порядок, в котором ротатор раздаёт запросы, от списка не зависит: берётся тот,
кто дольше всех не использовался (`_selectLeastUsedAccount` в
`src/utils/account-rotator.js`), а после старта приложения первый запрос уходит
не первому в списке `/api/getAllAccounts` (27.11: при списке #0, #1, #2 порядок
был #1, #2, #0; после перезапуска 02:35 UTC — #1, #2). Кто «использует» первый
аккаунт до первого запроса, не выяснено (гипотеза — загрузка списка моделей).
Только что добавленный аккаунт берёт следующий запрос: время его последнего
использования пусто. Планируя живую проверку по номеру аккаунта, — сначала
`v2-acc.sh state`, а не список.

### Уход клиента (Qwen2API-mxs)

Код на проде с 25.11 20:47 UTC (образ `ff8e6a7`); **проверен живьём 26.11**
(02:08 UTC, образ `fa7c9701` — «Проверено живьём» ниже). Клиент, ушедший до
конца ответа (таймаут n8n, закрытая вкладка), больше не оставляет генерацию
идти вхолостую: приложение закрывает upstream во всех текстовых потоковых путях
— `/v1/chat/completions` и `/v1/messages`, поток и без потока, с инструментами
и без; на egress это закрывает реле, воркер видит сокет `close` (~1 мс) и
отменяет `fetch` в странице. Закрытие — не ошибка: ни строки в логе, ни
списания с аккаунта, ни повтора и переключения аккаунта за ушедшего клиента.

**Почему так.** Под Bun (рантайм прода) сервер не сообщает об уходе клиента,
если тело запроса прочитано — а `express.json` читает его всегда: ни события,
ни флага, что при молчащем ответе, что при пишущемся кадрами. Единственный
след — сокет теряет адрес (`socket.address()` → `null`) через 1–6 мс.
`src/utils/client-gone.js` слушает `close` сокета (Node) и спрашивает адрес при
каждой проверке и каждые 250 мс (Bun). Замер 24.11 («сигнал под Bun есть»,
записан в `browser-egress-design.md`) делался запросом с непрочитанным телом и
приложение не описывает; полная матрица — там же, «Уход клиента под Bun —
уточнено 25.11».

**Что проверено без сети (25.11):** `tests/client-gone.test.js` (58 тестов,
гейт 1858/144); каждая защита правки сломана по одной — 42 мутации, каждая
поймана; сквозной смоук в топологии прода — приложение на
Bun 1.3.14, заглушка воркера на Node 24, настоящий клиент, egress-транспорт до
конца — из исходников и из скомпилированного бинарника, собранного из ветки:
8 ответов клиенту, который остался, 16 обрывов (оба API × поток и без потока ×
с инструментами и без × ответ идёт кадрами и модель молчит), реле закрыто
через 39–245 мс после ухода, в логе ни `[ERROR]`, ни `mid_stream_*`. Повторить
— образ с двумя рантаймами, оба образа уже есть на машине, сеть не нужна:

    printf 'FROM oven/bun:1.3.14-debian\nCOPY --from=node:24-slim /usr/local/bin/node /usr/local/bin/node\n' > Dockerfile
    docker build --network none --pull=false -t bun-node .
    docker run --rm --network none -v "$PWD:/work:ro" -w /work bun-node \
      node tools/client-gone-smoke.js --runtime bun

    # скомпилированный бинарник — нужен собранный public/dist
    docker run --rm --network none -v "$PWD:/work:ro" -v "$PWD/dist-bin:/out" oven/bun:1.3.14-debian \
      bash -c 'mkdir -p /src && cp -r /work/. /src/ && cd /src && bun --no-env-file tools/build-binary.mjs --target bun-linux-x64 --outfile /out/qwen2api'
    docker run --rm --network none -v "$PWD:/work:ro" -w /work -v "$PWD/dist-bin:/app:ro" bun-node \
      node tools/client-gone-smoke.js --runtime bun --binary /app/qwen2api

Смоук — под Node с `--runtime bun`, не под Bun: заглушка воркера должна стоять
на Node, потому что сервер на Bun, прочитавший тело, не видит и закрытия реле
приложением.

**Проверено живьём (26.11, 02:08 UTC, прод на образе `fa7c9701`).** Один запрос в
поток с длинным ответом (150 строк); клиент внутри контейнера приложения читал
поток и оборвал соединение, когда ответ только начался — после двух строк. У
воркера: `egress-stream /api/v2/chat/completions -> 200`, затем `… cancelled
(51839 ms)` — не `end`. `cancelled` воркер пишет только тогда, когда запрос в
странице действительно прерван: приложение закрыло реле, воркер увидел закрытие
сокета и отменил `fetch` в странице — вся цепочка, на этот раз с настоящей
страницей. Момент тот же: по часам клиента обрыв пришёлся на ту же секунду, что
и `cancelled` у воркера (точнее в этой записи не восстановить — скрипт тогда не
печатал абсолютного времени; теперь печатает). В логе приложения на запрос —
три строки (разбор запроса, «发送聊天请求» и предупреждение нормализатора
upstream о кадре `code_interpreter`, к уходу клиента не относящееся): ни
`聊天处理错误`, ни `mid_stream_`, ни `ERROR`, ни строки `usage` — списания с
аккаунта не было. У воркера один `chats/new` и один completions — ни повтора,
ни переключения аккаунта. Страница после обрыва осталась открытой (`residentPages
1` в `health` воркера); закрыта перезапуском воркера по правилу после живой
проверки.

**Что живьём не проверено:**

- **Обрыв через обратный прокси.** Проверка шла изнутри контейнера приложения,
  напрямую на `127.0.0.1:3000`, без прокси. Часть клиентов ходит через публичный
  домен (`qwen2api.web.codecitadel.ru`) — то есть через обратный прокси, а
  приложение слушает `0.0.0.0:3000`. Сигнал виден приложению, только если прокси
  закрывает своё соединение с приложением, когда уходит клиент (у nginx так по
  умолчанию — `proxy_ignore_client_abort off`; с `proxy_ignore_client_abort on`
  приложение об уходе не узнает, как и до правки). Какой прокси стоит перед
  продом и с какими настройками — не смотрел.
- **Обрыв, пока модель молчит.** В проверке кадры только пошли. Пока модель думает
  и ничего не шлёт, признак тот же — сокет теряет адрес, а приложение спрашивает
  его каждые 250 мс, — и сквозной смоук проходил оба варианта (ответ идёт
  кадрами и модель молчит); живьём второй не проверялся.

**Как проверить (один запрос; читается по логу воркера).** На хосте прода —
`bash /root/v2-abort.sh abort`: `POST /v1/chat/completions` в поток с длинным
ответом, клиент внутри контейнера приложения читает поток до первых кадров
ответа и обрывает соединение (`AbortController`; под Bun `reader.cancel()`
соединение не закрывает). Ключ приложения читается внутри контейнера, наружу не
печатается; заслон в минуту — общий с `/root/v2-media.sh`. Тот же скрипт:
`dry` — репетиция против заглушки на loopback внутри контейнера приложения (до
qwen.ai ничего не идёт: заглушка читает тело запроса, как его читает приложение,
и показывает, что после обрыва сокет теряет адрес — на проде через 11 мс);
`plain` — один текстовый запрос без потока, до конца. Ожидание: у воркера
`egress-stream … cancelled`, а не `… end`; в логе приложения на этом запросе ни
`聊天处理错误`, ни `mid_stream_`. После проверки — закрыть страницу (`bash

### Удаление аккаунта (Qwen2API-2l0, Qwen2API-u50; проверено живьём 27.11)

Удаление аккаунта в панели доходит до воркера (`POST /forget`): воркер снимает
сессию, закрывает страницу аккаунта и — при `SIGNIN_FORGET_DELETES_PROFILE=true`
(на проде так с 27.11) — удаляет профиль браузера: сразу (`profile deleted`), а с паузой `SIGNIN_FORGET_GRACE_MS` (Qwen2API-t8s, по умолчанию 2 минуты) — строкой `profile deleted after the pause` по её истечении; ответ `profile deferred` и «浏览器配置稍后删除» в логе приложения значат, что пауза началась. В логе приложения
`signin-worker 已忘掉账户 …（会话已清除，页面已关闭，浏览器配置已删除）` без
предупреждения, у воркера `forget session, page, profile deleted` и
`resident-close forgotten`. К qwen.ai это не обращается; `sessions` и
`residentPages` в `/health` падают на один, каталог профиля исчезает. Профили
адресов, которых в приложении уже нет, убираются тем же `/forget`
(`bash /root/v2-forget-stale.sh`, `apply` — с `CONFIRM=forget`; 27.11 так убраны
семь). `SIGNIN_FORGET_GRACE_MS` — переменная Compose: деплой, который заводит её
на проде, ставит ей Build time — снять по правилу о новых переменных Compose
(Qwen2API-9x1) выше в этом документе. С паузой `v2-forget-stale.sh` получает
`profile deferred`, и каталог профиля смотрят не сразу, а через паузу.

Запрос, который уже идёт через удаляемый аккаунт, после удаления до воркера
больше не доходит: ни `/egress`, ни `/renew`, ни `/session` за этот аккаунт,
страница заново не открывается, входа по паролю нет. Что видит клиент — зависит
от того, начался ли ответ:

- ответ ещё не начался — `503 upstream_error`, который можно повторить (так в
  смоуке на заглушке: она закрывает страницу сразу);
- стрим уже пошёл — `HTTP 200` и в конце кадр ошибки `upstream_stream_error` с
  `[DONE]`, не `503`. Так вышло живьём: `/forget` в воркере ждёт стримы страницы
  до предела (`resident-wait 1 still running (waited 20009 ms)`), всё это время
  ответ идёт клиенту, затем `resident-close forgotten`, у стрима `page_closed`, в
  приложении `聊天处理错误` (`page_closed`); `DELETE /api/deleteAccount` отвечал
  20,1 с (предел 35 с не исчерпан). Голова ответа уже ушла, сменить статус
  нельзя. Для стрима, ответ которого уже пошёл, NOTES Qwen2API-u50 такой исход
  допускают; считать ли его дефектом — за владельцем (на 27.11 не решено).

### Резидентные страницы

- **Когда открывается.** Лениво: при первом обращении аккаунта через `/egress`.
  Вход и продление сами по себе страницу не оставляют.
- **Сколько живёт.** До остановки воркера, вытеснения по лимиту или сбоя.
  Таймаута простоя нет: страница активного аккаунта остаётся открытой.
- **Сколько стоит.** Около 180 МБ на страницу у оболочки и около 340 МБ в
  `SIGNIN_HEADLESS_MODE=chrome` (Linux, замер 24.11). Десять аккаунтов — 1,8–3,4
  ГБ; на triglav свободно около 45 ГБ. Первое открытие в режиме `chrome` после
  старта воркера на секунду держит и второй браузер (воркер спрашивает у него
  имя) — ещё около 340 МБ.
- **Лимит `MAX_RESIDENT_PAGES` (по умолчанию 16; на проде — 20 с 27.11).** Когда он достигнут, перед открытием новой
  страницы вытесняется самая давно не использовавшаяся **свободная**. Занятая
  (есть вызовы в полёте, идёт вход или продление) не вытесняется никогда; если
  свободных нет, новый вызов получает `resident_capacity`, у клиента — `503`.
  Лечение — поднять лимит, не перезапускать.
- **Профиль принадлежит странице.** Chromium ставит блок на каталог профиля,
  поэтому пока страница жива, вход и продление этого аккаунта идут на ней.
- **Токен страницы (Qwen2API-xun).** Токен страницы живёт 15 минут, и сама
  страница обновляет его только перед своим запросом. С 26.11 воркер умеет
  обновлять его на месте перед вызовом, у которого токену осталось меньше 3
  минут, — тем же запросом, что делает фронт, без перезагрузки; простаивающие
  страницы не трогает.   **На проде включено с 27.11, 15:47 UTC** (образ `23cc3fd`,
  `SIGNIN_PAGE_TOKEN_REFRESH=true`): qwen.ai принимает обновление, если оно
  несёт заголовок `x-request-origin` с адресом самой страницы (PR #57; без
  него — `refused, status 200, code Bad_Request`, 4 из 4, ночь 27.11). Живой
  час 15:49–16:49 UTC: 12 обновлений на трёх страницах, 0 отказов, 0
  принудительных перезагрузок; около 1 с на первый вызов последних 3 минут
  цикла токена. Переключается без сборки: переменная runtime-only, Deploy без
  Stop.
- **Перезагрузка ждёт чужие ответы (Qwen2API-nch; на проде с 27.11, проверено живьём).** Продление,
  вход и принудительное восстановление не начинаются, пока на странице идёт
  стрим, — до `RESIDENT_STREAM_WAIT_MS` (20 с). Текст успевает, картинка и
  видео — нет. Пока навигация ждёт, новые вызовы аккаунта ждут тоже.
- **Загрузки по очереди (Qwen2API-nch, Qwen2API-ops; на проде с 27.11).** Каждый
  запуск, перезагрузка и продление любого аккаунта ждёт своей очереди —
  `RESIDENT_LOAD_MIN_INTERVAL_MS` (10 с + добавка до 10 с) от предыдущей
  загрузки любого аккаунта; ни одна не ждёт дольше
  `RESIDENT_LOAD_MAX_WAIT_MS` (2 минуты) — кроме одного случая: вход по
  паролю, начавшийся прямо перед её ходом, отодвигает её ещё на один
  промежуток, и не больше того, сколько бы входов ни началось. Более длинная
  очередь идёт теснее, тем же порядком. Полный вход по паролю в этой очереди
  не ждёт — его держит очередь входов. Пока продление аккаунта ждёт своего
  хода, вызовы этого аккаунта ждут вместе с ним (и принудительный вход тоже).
  После перезапуска воркера страницы открываются по одной: 16 аккаунтов —
  около двух минут на все.
- **Как смотреть.** `GET /health` воркера — `residentPages` и `maxResidentPages`,
  очередь загрузок `pageLoadQueue` (`waiting` — сколько ждут, `nextInMs` —
  сколько до ближайшего хода); каждая строка `egress …` воркера
  заканчивается на `(N/M pages)`.

### Headless-страница и `SIGNIN_HEADLESS_MODE`

Вход и продление на проде идут в headless и работают. Но headless-браузер
подписывает запросы словом «Headless», а единственная рабочая проба `chats/new`
от 23.11 не записала, в каком режиме она делалась.

**24.11, живьём: qwen.ai headless-страницу пускает.** Страница аккаунта
загружается, вход работает, её собственные запросы отвечают 200, и вызов
воркера из неё, посланный как её собственный запрос, проходит (повторная
выкатка, раздел «Результат живой выкатки 2026-11-24»). На первой выкатке отказ
получал вызов без заголовков страницы — и в режиме `chrome` точно так же. Для
completions (24.11: отказ в обоих режимах) рычаг тоже не помогает; он остаётся
на случай, если qwen.ai откажет самой headless-странице.

Если не пускает — `SIGNIN_HEADLESS_MODE=chrome`: воркер запускает полный Chromium
(он уже в образе) и предъявляет его как браузер с окном — на странице и внутри
стороннего iframe (там живёт капча). Против заглушки в образе воркера на Linux
этот режим не отличается от браузера в окне ни по одному замеренному полю
(`tools/worker-identity-probe.js`). Просто подменить строку User-Agent нельзя:
подсказки клиента продолжают говорить «HeadlessChrome», и страница противоречит
сама себе. Цена режима — память (см. выше). 24.11 в нём живьём открывалась
страница аккаунта; вход и капча в нём не проверялись.

Запуск с окном (`SIGNIN_HEADLESS=false`) переключателем не является: Xvfb в
образе воркера есть (ставится вместе с Chromium), но никто его не запускает —
дисплея у воркера нет. Это отдельная работа (запуск дисплея в entrypoint), а не
переменная.

### Часовое наблюдение

```sh
# что считала qwen.ai: страницы, вызовы, перезагрузки, входы
docker logs --since 1h <signin-worker-контейнер> 2>&1 | node tools/egress-log-watch.js
# что из этого видело приложение: отказы, восстановление, входы
docker logs --since 1h <qwen2api-контейнер>     2>&1 | node tools/egress-log-watch.js
```

Счётчик читает только текст и заканчивает вердиктом: `LOOK` с перечнем причин
(код выхода 1), `OK` (0) или `NOTHING TO JUDGE` — в логах нет ни одного вызова
(код 2). Причина важнее «нечего судить»: воркер, который даже не открыл страницу,
даёт `LOOK`, а не пустой час. Ошибки приложения, которых он не знает, он
перечисляет. Ему нужны Node и репозиторий на той машине, где читают логи; в
контейнере его нет.

По сохранённым логам — та же подача без `docker logs`. Пересоздание контейнеров
уносит их журналы, поэтому до каждого деплоя на хосте делают `bash
/root/v2-save-logs.sh <имя>`: он кладёт `worker.log` и `app.log` в
`/root/v2-logs-<имя>` (режим 700) и рядом копии с маскированными адресами
(`*.masked.log` — для чтения людьми). Счётчику нужны исходные строки (JWT в них
нет); копии можно забрать на машину разработки и считать там:

```sh
cat v2-logs-20261127-rollout-a/worker.log v2-logs-20261127-rollout-a/app.log \
    | tr -d '\r' | node tools/egress-log-watch.js
```

Каталоги двух окон подаются одной командой — счётчик считает по строкам, а не по
времени. Логи окна `a` выкатки 27.11 сняты при включённом обновлении токена на
месте: их `LOOK` читают по строкам таблицы «(образ с Qwen2API-xun)», числа —
«Состояние на 27.11» в конце.

Час с клиентами читают так же — своих запросов за час не шлю. В конце часа, до
любого деплоя или перезапуска, — `bash /root/v2-save-logs.sh first-hour`; оба
лога забирают на машину разработки (`scp`: на хосте нет ни `node`, ни `tools/`),
счётчик пускают отдельно по `worker.log` и по `app.log`; глазами читают
маскированную копию (`app.masked.log`): в немаскированной строке `v2 会话已续期`
стоит полный адрес аккаунта. Фоновой трафик открытых страниц воркер в лог не
пишет; его меряют счётчиками интерфейсов контейнера воркера
(`/sys/class/net/*/statistics/rx_bytes` и `tx_bytes` внутри контейнера, все
интерфейсы, кроме `lo`) — вместе с трафиком самих запросов, отдельно фон не
выделить. `docker stats` для этого не годится: показывает один интерфейс (около
10 КБ), а страницы ходят через другой (около 3,6 МБ на загрузку страницы), и
номер интерфейса меняется при пересоздании контейнера.

Счётчику нужны реальные вызовы, иначе он отвечает `NOTHING TO JUDGE`. Когда
клиентов нет (ключ сменён), час делают сами: шесть запросов в приложение с хоста
прода — по одному раз в 10 минут, чередуя поток и без потока, один-два — с
документом в промпте; первый — картинка в сообщении на только что открытой
странице (закрыть её перед этим: `bash /root/v2-media.sh close`). Минуты брать
вдали от тиков таймера продления токенов приложения (26.11 — `:05`, `:20`, `:35`, `:50`; время идёт от старта контейнера приложения — 27.11 первый тик был в 01:53:19 UTC, через 13 минут после старта) —
его продление перезагружает страницу; на образе с Qwen2API-nch перезагрузка
сначала ждёт идущий стрим — до 20 с, дольше обрывает. После последнего
запроса — снова закрыть страницу. 26.11 расписание было таким: 02:12:30, :22:30,
:32:30, :42:30, :52:30, 03:02:30 UTC (`picmsg`, `pong`, `doc`, `pong`, `doc`,
`pong`); сам час — ниже, «Как прошёл час».

Что считается нормой за час (и что счётчик проверяет):

Генерации по-прежнему падают: их запросы идут из Node и curl-impersonate, которые

Последнее — почему «как до выкатки» верно лишь без трафика. Старый код на
чужой падающий запрос не ходил в браузер вовсе. Новый на каждый отказ сессии
делает настоящую перезагрузку страницы (не чаще одной в 30 с на аккаунт), а
когда перезагрузка не помогает — полный вход по паролю (60 с, удвоение до 15
мин). Поток 68 запросов в час превращается в поток перезагрузок и по четыре
входа в час. Поэтому деплой с выключенными флагами делается при отрезанных
клиентах, и в таком же состоянии прод надолго не оставляют.

Про Stop в Coolify. Через API — с `"docker_cleanup": false`
(`POST /api/v1/applications/<uuid>/stop`): без этого флага Coolify ставит чистку
Docker на весь сервер (при заполнении диска от 80 % она чистит кэши сборки). И
стек нельзя оставлять остановленным на 00:00 UTC: ежедневная чистка удаляет
неиспользуемые томы (в настройках сервера включено `delete_unused_volumes`), а
профили Chromium лежат в томе `…_signin-profiles`.

### Откат

Тремя уровнями, от мягкого к полному.

**Цена изменения переменных в Coolify (с 25.11, Qwen2API-3ue.8).** Смена
значения → Deploy **без Stop** → около 35 секунд от постановки в очередь до
конца, из них контейнеры пересоздаются 15–30 секунд; для того же коммита
Coolify пропускает сборку («Build step skipped»). Возврат `API_KEY` — тоже
смена переменной и стоит тех же 35 секунд. При включённом egress ключ
возвращают сразу; при выключенном — только вместе с уровнем 2, иначе получится
поток перезагрузок и входов (шаг 2).

До 25.11 смена переменной была полной пересборкой обоих образов с загрузкой
Chromium (24.11: 7,5 минуты простоя, следующая — 38,5 при CDN около 75 КБ/с).
Причина была не в Dockerfile'ах — своих `ARG` под переменные стека в них нет:
Coolify передаёт в сборку каждую переменную с флагом «Build time», дописывает
под неё `ARG` в каждую стадию Dockerfile и теряет кэш всех последующих `RUN`,
когда значение меняется. С 25.11 переменные стека стоят как runtime-only
(`is_buildtime=false` в API); в логе деплоя при этом — «No build-time variables
to add to Dockerfiles» и команда сборки без `--build-arg`. Если у переменной
снова включить «Build time», всё вернётся как было.

Три правила, которые остались:

- **перед Deploy не делать Stop.** Сборка идёт при живых старых контейнерах, и
  простой — только пересоздание. Со Stop простоем становится вся сборка;
- **первый деплой после 00:00 UTC — всегда полный.** Ежедневная чистка на
  сервере (`force_docker_cleanup`, `0 0 * * *`) выполняет `docker builder prune
  -af` и стирает кэш сборки, так что Chromium качается заново: 25.11 в 07:27 —
  4 минуты при быстром CDN, 24.11 — до 38 минут при медленном. На простой это не
  влияет, если не делать Stop; отдельной настройки для этой части чистки в
  Coolify 4.7.6 нет.

- **новую переменную compose Coolify заводит с флагом «Build time»**
  (Qwen2API-9x1): деплой, впервые встретивший переменную в compose-файле,
  создаёт её с `is_buildtime=true` — и первая же смена её значения стоила бы
  пересборки. 27.11 так встали пять переменных пачки (`RESIDENT_STREAM_WAIT_MS`,
  `RESIDENT_LOAD_MIN_INTERVAL_MS`, `RESIDENT_LOAD_MAX_WAIT_MS`,
  `SIGNIN_PAGE_TOKEN_REFRESH`, `SIGNIN_TOKEN_REFRESH_MIN_INTERVAL_MS`); в 02:35 UTC
  флаг снят (`PATCH /applications/<uuid>/envs` с `is_buildtime=false,
  is_runtime=true`, значения не менялись). После каждого деплоя с новой
  переменной — проверять список переменных (команда — «Переменные», «Флаги новых
  переменных в Coolify»); хелпер, создающий переменную без явного флага, для
  стека не годится.

1. **Выключить egress** — `CHAT_CREATION_TRANSPORT=direct`,
   `COMPLETIONS_TRANSPORT=auto` (если меняли — и `SIGNIN_HEADLESS_MODE=shell`).
   Поведение возвращается к состоянию до включения флагов. На заблокированном IP
   это значит: генерации снова падают, как 23.11, — но уже с настоящими
   перезагрузками и входами по паролю (с дросселями), пока запросы приходят.
   Откат возвращает прежнее состояние, а не работоспособность. **Пока прямой
   путь с этого IP отказан (блок с 21.11), выключать egress хуже, чем держать
   включённым.** С включёнными флагами отказ completions не запускает
   восстановления: клиент получает `503`, перезагрузки и входы не идут (24.11).
   С выключенными прямой путь на каждый отказ даёт настоящую перезагрузку
   страницы и, если она не помогла, парольный вход. 24.11 по этой причине флаги
   оставили включёнными.
2. **Вернуть образ** — передеплоить прежний образ (PR `production` назад или
   деплой предыдущего коммита). Нужен при отказе самого деплоя — и когда прод
   оставляют надолго с падающим трафиком: старый код в браузер не ходил, новый
   ходит.
3. **Полный откат на v1-путь** — `V2_SESSION_MODE=off` + `COMPLETIONS_TRANSPORT=axios`
   (раздел «Откат» выше). Входы по v1 с заблокированного IP не проходят.

**Шаг 3а.** Режим `chrome` (проверен той же пробой, в Coolify не включался) —

**Контрольная проба — прошло.** Тот же вызов, посланный так, как его шлёт сама
страница: через XMLHttpRequest, с её заголовками, через 20 секунд после
готовности страницы, в `shell`. Ответ: `HTTP 200`, `{"success":true,…}` —
создан пустой чат, капчи нет (`--transport=xhr --like-fe=1 --settle-ms=20000`).

**Что из этого следует.** Вызов из страницы должен быть похож на запрос самой
страницы: нести её заголовки. Первая версия причины — «нет подписи Baxia
(`bx-ua`, `bx-umidtoken`)» — не подтвердилась: в прошедшем сеансе подписи не было
ни в одном запросе, перехватчик добавил только `bx-v`; в другом сеансе она была
у двух запросов страницы. Подпись ставится непостоянно и не обязательна.

заголовками, нужно ли ожидание перед первым вызовом. Для правки не требуется:
слать через XHR со всеми заголовками страницы — тогда перехватчик добавляет
нашему запросу то же, что своим. Заведено: Qwen2API-3ue.5 (транспорт и
заголовки), Qwen2API-3ue.6 (распознать такой отказ сразу, а не «страница не
отвечает»).

**Правка по итогам (Qwen2API-3ue.5 и 3ue.6).** Что сделали и что выяснили по
дороге — подробно в `docs/browser-egress-design.md`, разделы «Вызов как запрос
самой страницы» и «Страница-проверка видна сразу»; коротко:

- Вызов воркера уходит из страницы как её собственный запрос: XMLHttpRequest
  (так шлёт свои запросы к API код страницы, и так их подписывает её
  перехватчик), с заголовками страницы. Заголовки страницы читает сама
  страница — не приложение: у прямого пути они из отпечатка аккаунта (язык

- Находка, которой не было в описании задачи: `accept-language` ставит сама
  страница (`en-US,en;q=0.9`), а не браузер (браузер подставил бы только

  ответ сразу; а если бы скрипты страницы удержали и его — воркер читает ответ
  из сети страницы. В логе воркера такая строка названа: `— WAF challenge
