# Qwen2API с signin-worker sidecar (v2 session pipeline)

`docker/docker-compose.signin.yml` — самостоятельная альтернатива
`docker/docker-compose.dev.yml` (как и DNS-вариант): Qwen2API плюс sidecar
`signin-worker`, который получает и тихо продлевает сессии chat.qwen.ai в
настоящем Chromium (Playwright). Обоснование и живые доказательства —
`docs/et0-live-integration-2026-11-21.md` и `docs/hybrid-v2-pipeline-design.md`
(epic Qwen2API-jik, задача jik.3).

## Зачем

Вход по паролю в v2 из чистого Node заблокирован WAF (интерактивный слайдер
Aliyun/Baxia, HTML вместо JSON). В реальном браузерном контексте капча
проходит сама. Поэтому вход выделен в sidecar-сервис, а сам чат-конвейер
остаётся на HTTP: сессия (JWT ~30 мин + cookies) передаётся в cookie-jar
адаптера (`src/utils/v2-session-store.js`).

## API sidecar (только внутренняя сеть)

- `POST /session {email, password, proxy?, force?}` → `{token, expiresAt, cookies[], …}` —
  полный вход через форму `chat.qwen.ai/auth` (пароль в открытом виде: форму
  хеширует сам FE) — но только если у воркера нет живой сессии этого аккаунта
  (см. «Полные входы: без повторов и по очереди»).
- `POST /renew {email, proxy?, force?}` → та же форма ответа — тихое продление:
  перезагрузка chat.qwen.ai в персистентном профиле (пароль не нужен).
  Пока токен из кэша свеж, ответ отдаётся из кэша без запуска браузера.
  `force: true` — явная инвалидация (Qwen2API-3ue.2): сессию отказали на
  upstream, поэтому ответ обязан быть живой перезагрузкой, даже пока токен из
  кэша не истёк; отказанная запись кэша сбрасывается до перезагрузки.
  Перекрывающиеся по времени продления схлопываются в одну перезагрузку —
  принудительные и обычные, включая тихое продление по таймеру.
- `GET /health` → `{ok, sessions, residentPages, maxResidentPages}`.
- `POST /egress {email, url, method, headers, body, timeoutMs, proxy?}` →
  `{status, headers, body, url, redirected, cookies[]}` — запрос к qwen.ai **изнутри
  резидентной страницы** аккаунта (`page.evaluate` + `fetch` с
  `credentials:'include'`): upstream видит TLS и живые cookies браузера.
  Страница открывается лениво, по первому обращению, и остаётся жить.
  Разрешены только адреса origin чата; заголовок `cookie` игнорируется (банка —
  браузерная). HTTP-код воркера здесь всегда `200`, когда egress состоялся:
  код и тело ответа qwen.ai лежат внутри. Без стриминга (E.3).

Один Chromium-профиль (`userDataDir`) на аккаунт — каталог `account-<sha256(email)>`
в `/app/profiles` (volume): cookies auth.qwen.ai переживают рестарты, продление —
молчаливый reload. Воркер сам держит сессии тёплыми: таймер продлевает токен на
отметке ~60% остаточного TTL. Пароли нигде не хранятся и не логируются; email
не попадает ни в логи, ни в имена файлов; логи содержат только коды исходов.

Пока страница аккаунта резидентна, она **владеет** профилем (Chromium ставит
блок на каталог): `POST /session` и живой `POST /renew` исполняются на ней, а не
во втором браузере. Жизненный цикл страниц (лимит `MAX_RESIDENT_PAGES`, keep-alive,
краши, остановка) и полный контракт `/egress` — в
`docs/browser-egress-design.md`.

Проверено живьём 2026-11-21 (headless, капча Aliyun проходит сама): вход даёт
короткий токен (~15–30 мин), но первый же reload в залогиненном профиле
ротирует его на ~30-дневный (HttpOnly `refresh_token`) — воркер выходит на
длинные токены автоматически первым же тихим продлением.

## Полные входы: без повторов и по очереди (Qwen2API-43a)

Полный вход — самое заметное для защиты qwen.ai (Baxia) действие. 23.11 один
«добавить аккаунт» на проде обернулся тремя входами за 4 секунды, а пачка
входов с одного IP 21.11 закончилась блокировкой всего IP. Поэтому воркер
делает три вещи.

**Живая сессия вместо входа.** Если у воркера уже есть живая сессия аккаунта
(`exp > now + 120 s` — тот же порог, при котором `/renew` отвечает из кэша),
`POST /session` отдаёт её и браузера не касается. Пароль при этом не
проверяется — как и раньше: на уже залогиненном профиле `/auth` закрывается
редиректом, и вход проходил без проверки пароля.

**Один вход на всех ждущих.** Если вход для аккаунта уже идёт, новый
`POST /session` для него не встаёт в очередь за блокировкой профиля, а ждёт
тот же результат (успех или ошибку — одну на всех). Три запроса за 4 секунды
— один вход.

**По очереди и с паузой.** Каждый вход, который всё же выполняется, берёт
слот в общей очереди воркера (`signin-worker/lib/login-pacer.js`): следующий
начинается не раньше чем через `SIGNIN_LOGIN_MIN_INTERVAL_MS` после начала
предыдущего, плюс случайная добавка до того же значения (по умолчанию пауза
30–60 с). Очередь одна на весь воркер, то есть на весь IP. Тихие продления
(`/renew`) и леничное открытие резидентной страницы — обычные загрузки
страницы, как вкладка в браузере; через очередь они не проходят. Неудачный
вход слот занимает: именно отклонённые попытки защита и считает.

Запрос, которому ждать дольше `SIGNIN_LOGIN_MAX_WAIT_MS`, сразу получает
`429 {code: "signin_paced", retryAfterMs}` и **слот не занимает**: ни один
HTTP-запрос не висит минутами, и ни один вход не выполняется, когда его уже
никто не ждёт. Приложение показывает это как `signin_busy` («слишком много
входов подряд, подождите»).

`force: true` просит настоящий вход, несмотря на живую сессию, — для случая,
когда закэшированную сессию только что отверг upstream. Так его использует
восстановление E.2 (ниже): полный вход после отказанной сессии всегда идёт с
`force: true`, иначе воркер вернул бы ту сессию, которую только что отказали.

Цена: когда приложению нужно N полных входов подряд (массовый импорт,
`ACCOUNTS` при `DATA_SAVE_MODE=none` на старте), они идут по одному и
занимают N × (30–60 с + сам вход). Пока воркер держит живые сессии, `/session`
отвечает мгновенно.

Очередь живёт в памяти воркера: после его рестарта отсчёт начинается заново,
первый вход не сверяется с последним входом до рестарта.

## Конфигурация приложения

| Переменная | Назначение |
| --- | --- |
| `V2_SESSION_MODE` | `off` (по умолчанию, нынешний v1-путь) \| `lab` (.test-стенд, см. `tests/v2-lab-sessions.test.js`) \| `browser` (сессии из sidecar). Заданный `QWEN_LAB_V2_AUTH_ORIGIN` без явного режима по-прежнему включает `lab` |
| `SIGNIN_WORKER_URL` | URL воркера, по умолчанию `http://signin-worker:3100` |
| `SIGNIN_WORKER_TOKEN` | Общий bearer-секрет приложение → воркер; пусто = без авторизации (только внутренняя сеть) |
| `AUTO_REFRESH_INTERVAL_SECONDS` | Каденс авто-refresh токенов; в `browser`-режиме по умолчанию 15 мин вместо 6 ч (токен живёт ~30 мин) |
| `SIGNIN_WORKER_TIMEOUT_MS` | Бюджет вызова воркера, по умолчанию `240000`. `/session` сначала ждёт свой слот в очереди входов, поэтому значение должно быть больше `SIGNIN_LOGIN_MAX_WAIT_MS + SIGNIN_TIMEOUT_MS` воркера — иначе приложение откажется от входа, который воркер всё равно выполнит |
| `CHAT_CREATION_TRANSPORT` | `auto` (по умолчанию: `browser`, когда `V2_SESSION_MODE=browser` **и** задан `SIGNIN_WORKER_URL`, иначе `direct`) \| `browser` (принудительно; требует `V2_SESSION_MODE=browser`, иначе приложение не стартует) \| `direct` (axios, прежнее поведение). Compose отдаёт `direct` — egress выключен, пока его не включат явно. Прокинут в Compose |
| `V2_SESSION_RECOVERY_MIN_INTERVAL_MS` | `30000`. Не чаще одного восстановления сессии на аккаунт в этот интервал: отклонённая сессия не перезагружает страницу на каждый неудачный запрос. `0` отключает |
| `V2_SESSION_RELOGIN_MIN_INTERVAL_MS` | `60000`. Минимум между полными входами по паролю на аккаунт (входы кормят скор Baxia). После каждой попытки, не давшей принятой сессии — провалившейся или отклонённой, — ожидание удваивается, до 15 мин. `0` отключает |

В `browser`-режиме `TokenManager.login` делает `POST /session`, а refresh —
`POST /renew` c откатом на полный вход, когда профиль умер (`no_profile` /
`session_expired`). Cookies сессии едут в запросах `chats/new` и completions
через тот же jar-механизм, что доказан в lab (`v2-session-store.prepareChat`);
аккаунтный прокси при этом сохраняется.

Приложение не просит у воркера лишних входов (Qwen2API-43a):

- «Добавить аккаунт» — один вход. Раньше `/setAccount` входил, а сохранение
  (`saveAccounts`) входило второй раз, выбросив уже полученный токен.
- В `browser`-режиме массовый импорт идёт **по одному аккаунту**
  (`BATCH_LOGIN_CONCURRENCY` не действует): параллельные входы всё равно
  встали бы в очередь воркера или получили бы `signin_paced`. Так же по
  одному логинятся аккаунты из `ACCOUNTS` на старте. В остальных режимах
  настройка действует как раньше.
- Кнопка «Добавить» не отправляет форму повторно, пока идёт вход.

### Chats/new через воркер и восстановление сессии (Qwen2API-3ue.2)

С `CHAT_CREATION_TRANSPORT=browser` (или `auto` в browser-режиме) создание
чата уходит не из Node, а `POST /egress` — изнутри резидентной страницы
аккаунта (`src/utils/browser-egress.js`). Ответ qwen.ai классифицируется так
же, как прямой (`assertChatCreationResponse`): клиент видит те же коды. Воркер,
который не смог обслужить вызов (недоступен, `page_closed`, `egress_timeout`,
лимит страниц…), — это **громкий** `503 upstream_transport_error` с кодом
воркера в логе; приложение никогда не подменяет такой вызов прямым запросом из
Node TLS. Откат — `CHAT_CREATION_TRANSPORT=direct` одной переменной, без
передеплоя.

- **Синхронизация cookies.** Банка браузера (`cookies[]` из каждого `/egress`)
  вливается в сессию аккаунта: cookie, выставленная сервером, побеждает
  хранимую с тем же именем и скоупом, остальные живут. Изменившаяся банка
  дописывается и в хранилище (файл/Redis). Прямые вызовы текстового конвейера,
  которые остаются (completions до E.3, `chats/new` в `direct`), точно так же
  вбирают `Set-Cookie` своих ответов. Вызовы картинок/видео jar не используют.
- **Восстановление в запросе.** `unauthorized` / WAF-challenge / мёртвый профиль
  на egress → перезагрузка страницы (`/renew` с `force`) → ровно один повтор
  `chats/new` в том же запросе; мёртвый профиль → полный вход по паролю. Сессия
  при этом не сбрасывается — ни при отказе, ни при `401` прямого completions.
- **Полный вход — только за отказанную сессию.** Перезагрузили — и снова
  `unauthorized`: следующий шаг полный вход, в фоне. Он всегда идёт как
  `/session {force: true}`: обычный `/session` при живой сессии воркера ответил
  бы той самой сессией, которую только что отказали. Между аккаунтами входы
  строит очередь воркера (Qwen2API-43a). WAF-challenge пароля не стоит: он
  получает перезагрузку с повтором на egress и ничего — на прямом пути.
- **Токен следует за сессией.** Продление ротирует токен; запись аккаунта
  подхватывает его на месте (память + хранилище), поэтому генерация, начатая на
  старом токене, продолжается на новом без `409 v2_session_required`.
- **Дроссели.** Восстановление — single-flight на аккаунт и не чаще
  `V2_SESSION_RECOVERY_MIN_INTERVAL_MS`; полный вход — не чаще
  `V2_SESSION_RELOGIN_MIN_INTERVAL_MS`, а каждая попытка, не давшая принятой
  сессии (в том числе провалившаяся), удваивает ожидание — до 15 мин. Пока
  входу надо ждать, восстановление делает перезагрузку. Запрос, попавший в
  окно, сразу получает свой отказ без повторной перезагрузки.
- **Инвалидация прямого пути.** `401` на прямом вызове по-прежнему сбрасывает
  сессию, но продление теперь живое (`force`), а внутри окна восстановления
  инвалидация ничего не меняет. WAF-challenge на прямом пути не меняет ничего.

Откат: `V2_SESSION_MODE=off` возвращает v1-путь одной переменной; sidecar
останавливается независимо.

**Важно для деплоя:** Compose отдаёт `CHAT_CREATION_TRANSPORT=direct`, то есть
egress **выключен**, пока его не включат явно (`browser`). Значение `auto` для
приложения без Compose — по умолчанию, но в прод-окружении
(`V2_SESSION_MODE=browser` + `SIGNIN_WORKER_URL`) оно означает `browser`, то
есть «включено сразу с этим кодом»: для выката с выключенными флагами его не
задавать.

## Переменные воркера

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SIGNIN_WORKER_TOKEN` | пусто | Общий bearer-секрет; пусто = без авторизации (только внутренняя сеть) |
| `SIGNIN_HEADLESS` | `true` | `false` — с видимым окном |
| `SIGNIN_TIMEOUT_MS` | `120000` | Бюджет браузерных потоков (вход, ожидание токена); для `/egress` — `timeoutMs` по умолчанию |
| `MAX_RESIDENT_PAGES` | `16` | Лимит резидентных страниц (~200–300 МБ Chromium на каждую). Прокинут в Compose |
| `RESIDENT_KEEPALIVE_MS` | `300000` | Период, с которым воркер читает живую банку cookies страницы |
| `SIGNIN_EGRESS_MAX_TIMEOUT_MS` | `600000` | Потолок `timeoutMs` запроса `/egress` |
| `SIGNIN_LOGIN_MIN_INTERVAL_MS` | `30000` | Минимальная пауза между полными входами (+ случайная добавка до того же значения); `1` — выключить очередь. Прокинут в Compose |
| `SIGNIN_LOGIN_MAX_WAIT_MS` | `120000` | Сколько `/session` может ждать свой слот в очереди входов; дольше — сразу `429 signin_paced`. Прокинут в Compose |

Compose передаёт воркеру только то, что перечислено в `environment:` сервиса
`signin-worker`: `SIGNIN_WORKER_TOKEN`, `SIGNIN_HEADLESS`, три переменные
резидентных страниц и две переменные очереди входов. `SIGNIN_TIMEOUT_MS`,
`SIGNIN_MIN_RENEW_DELAY_MS` и `SIGNIN_CHAT_ORIGIN` задаются только при запуске
воркера вне Compose.

## Сборка и запуск

Воркер собирается из `signin-worker/` (node:20-slim + Playwright 1.65.1 +
Chromium; сам пакет playwright требует Node ≥ 20). Порты наружу не
публикуются: API переносит пароли и bearer-токены. healthcheck — `GET /health`.

```sh
docker compose --project-directory . --env-file /secure/signin.env -p qwen-signin-test \
  -f docker/docker-compose.signin.yml config --quiet
docker compose --project-directory . --env-file /secure/signin.env -p qwen-signin-test \
  -f docker/docker-compose.signin.yml up -d --build --wait
```

Пример env — `docker/signin.env.example` (копировать в приватный файл вне Git).
Volume `signin_profiles` хранит браузерные профили: в них лежат живые сессии
(эквивалент bearer-токенов) — защищайте его как данные аккаунтов. Для bind-mount
каталог на хосте должен быть доступен на запись UID 10001 (пользователь `app`
в образе). Coolify: существующий ресурс, Base Directory `/`, Compose Location
`/docker/docker-compose.signin.yml` (как в DNS-варианте, см. `docs/dns-sidecar.md`);
профили можно оставить named volume. Для прода вместе с DNS-sidecar используйте
`/docker/docker-compose.prod.yml` (см. `docs/prod-hybrid-deploy.md`).

Пер-аккаунтные прокси: приложение передаёт `account.proxy` (или глобальный
`PROXY_URL`) в каждом запросе к воркеру; браузерный контекст запускается через
него (http/https/socks5). То же поле можно передать и в `/egress`: без него
страница откроется через прокси, который воркер помнит за аккаунтом.

## Локальный смоук egress без qwen.ai

`tools/worker-egress-local-smoke.js` прогоняет настоящий воркер с настоящим
headless Chromium — но «чатом» служит заглушка на 127.0.0.1, которая выставляет
cookie и токен и показывает, что до неё дошло. qwen.ai не касается, можно
запускать свободно (это не живая проба). Юнит-тесты работают с фейковым
Playwright; этот смоук — единственный способ без выхода в интернет убедиться,
что cookie профиля реально уходят с запросом, а чистая остановка сбрасывает
профиль на диск. Он же проверяет вход настоящим браузером (Qwen2API-43a):
полный вход на резидентной странице, ответ `/session` из живой сессии без
загрузки страницы и ожидание слота перед следующим входом — и явную
инвалидацию (Qwen2API-3ue.2): `/renew {force}` перезагружает страницу вопреки
свежему кэшу, а пачка таких запросов схлопывается в одну перезагрузку. Запускать после
правок `signin-worker/server.js`, `signin-worker/lib/login-pacer.js`,
`signin-worker/lib/resident-pages.js` и `signin-worker/lib/egress-fetch.js`:

```sh
bunx playwright install chromium   # один раз
node tools/worker-egress-local-smoke.js
```

## Локальный harvest без Docker

Инструмент `tools/v2-session-harvest.js` проводит тот же вход и кладёт сессию
в `.tmp/session-<email>.json` (gitignored) — это разблокирует ручные пробы
jik.2 с живым токеном. Профиль переиспользуется: повторный запуск (`renew`)
проверяет тихое продление.

```sh
bun install && bunx playwright install chromium   # один раз
QWEN_TEST_EMAIL=… QWEN_TEST_PASSWORD=… node tools/v2-session-harvest.js
QWEN_TEST_EMAIL=… QWEN_TEST_PASSWORD=… node tools/v2-session-harvest.js renew
```

Креденшелы передаются только через env; stdout содержит имена cookies и срок
токена, но не значения. `HARVEST_HEADFUL=1` — запуск с видимым окном (если
headless начнёт помечаться WAF; в контейнере это потребует xvfb).

- `tests/signin-worker-service.test.js` — сам воркер с фейковым браузерным
  модулем: кэш, тихое продление, сериализация запусков на профиль, коды ошибок.
- `tests/signin-worker-pacing.test.js` — очередь полных входов и дедуп
  `/session`: слоты и пауза между входами, отказ `signin_paced` без слота,
  живая сессия вместо входа, `force`, один вход на всех ждущих, продление
  вне очереди.
- `tests/signin-login-dedupe.test.js` — половина приложения: один «добавить
  аккаунт» = один вход и сохранение полученного токена, массовый импорт по
  одному в `browser`-режиме, кнопка «Добавить» без повторной отправки.
- `tests/signin-worker-egress.test.js` — резидентные страницы и `/egress` с
  фейковым «Playwright»: страница исполняет настоящую в-страничную функцию в
  песочнице с подконтрольным `fetch`. Разрешённые адреса, прокидывание
  заголовков, ленивое открытие, повторное использование страницы входом и
  продлением, лимит и вытеснение, keep-alive, краши, остановка, явная
  инвалидация `/renew {force}`.
- `tests/browser-egress.test.js` — приложение против stand-in воркера на
  loopback: транспорт по `CHAT_CREATION_TRANSPORT`, форма запроса `/egress`,
  классификация ответов, синхронизация jar, восстановление в запросе и его
  дроссели, подхват токена записью аккаунта.
- `tests/v2-session-persistence-file.test.js` — хранение сессий и восстановление
  уровня хранилища: живое продление, лимит полного входа, гонки, запись jar.

Chromium в CI не нужен: зависимость playwright в sidecar ленивая, тесты
инжектируют фейковый signer.
