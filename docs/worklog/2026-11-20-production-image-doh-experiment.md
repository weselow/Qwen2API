# Штатный production image Qwen2API с динамическим DNS-over-HTTPS

20 ноября 2026; измерения 18:18–18:20 UTC / 22:18–22:20 Europe/Saratov.
Задача эксперимента: Qwen2API-0uv. Неуспешная генерация: Qwen2API-5s6.

## Результат

Динамический DoH убрал зависание каталога **на штатном production image**, без lab-патчей. С обычным DNS каталог не ответил за 16 секунд; с DoH вернул HTTP 200 и 14 моделей за 2.127 секунды. Контрольная генерация после этого вернула HTTP 502 upstream_error за 0.293 секунды. Полная работоспособность Chat Completions не подтверждена; потоковую проверку не запускали, повторов не было.

Это разделяет два препятствия: выбранный обычным DNS недоступный endpoint и оставшийся быстрый upstream-отказ при генерации. Причину второго по полученному штатному ответу установить нельзя. HTTP 502 не объявляется доказательством WAF, истечения JWT или ошибки DNS.

## Динамический DNS

Sidecar использует python:3.13-alpine, фактически image ID / digest sha256:9ef1a599f863231c3d91e941389bfdc4a2d6070557243d54df1a4e57015b960e. Никаких библиотек на production host не устанавливалось. Sidecar без опубликованных host ports, UID 65534, read-only root, ограничен по памяти/CPU; приложение обращается к нему через --dns 172.23.254.53. Этот адрес — внутренний адрес DNS-сервиса, не закреплённый Qwen/CDN IP.

Путь: штатный Qwen2API → Docker 127.0.0.11 → DNS sidecar → HTTPS POST cloudflare-dns.com/dns-query с DNS wire message и стандартной проверкой TLS. Имена qwen.ai / *.qwen.ai и текущая зона CNAME aliyunga0019.com направляются через DoH. Остальные имена, включая bootstrap resolver endpoint, разрешаются через обычную локальную цепочку. При сбое DoH для Qwen возвращается SERVFAIL; отката Qwen на обычный DNS нет.

Sidecar не содержит Qwen IP, не переписывает A-записи, не имеет своего кэша и передаёт полученные TTL. ExtraHosts у диагностических приложений не заданы. UDP и TCP DNS проверены. Безопасный DNS-журнал содержит только qname/qtype/A/TTL/rcode и тип транспорта; HTTP headers/cookies/JWT в него не попадают.

Наблюдались A=170.33.12.244 с TTL 529, 579, 437 и 559 секунд; AAAA — NOERROR без адресов. Отдельная проверка из network namespace DoH-приложения через его реальный Docker DNS @127.0.0.11 также вернула A=170.33.12.244. Это фактическая resolver-цепочка приложения, а не только host curl с --doh-url.

Накопление кэша Docker/Bun за длительное время и поведение после смены CDN IP не исследованы. Работоспособность нынешнего DoH endpoint не гарантирует неизменности его PoP/ответов.

## Сравнение

| Проверка | Обычный DNS | Динамический DoH |
|---|---|---|
| Image / SHA бинарника | штатные, идентичные | штатные, идентичные |
| /v1/models через Qwen2API | client TimeoutError, 16.158 s | HTTP 200, 14 моделей, 2.127 s |
| qwen3.7-plus в каталоге | ответа не получено | присутствует |
| Один non-stream запрос «Reply with exactly OK» | не запускался | HTTP 502, upstream_error, 0.293 s |
| Stream | не запускался | пропущен после неуспешного non-stream |

У обоих приложений свежий процесс без старого models cache. В исходнике getLatestModels при первом upstream-сбое возвращает пустой список, а не статический набор. Поэтому положительный список из 14 моделей показывает получение каталога, а не только живую Express-страницу. Приложение кэширует модели; конфигурация MODELS_CACHE_TTL=1 одинакова в обоих контейнерах.

При 502 распознаваемых строковых признаков captcha/challenge/aliyun_waf либо unauthorized/invalid-token/expired-token в ответе не обнаружено. Отсутствие этих признаков **не исключает** WAF или отказ авторизации: штатный generateChatID сворачивает разные ошибки и отсутствие data.id в null. Связанный известный дефект Qwen2API-2ij существует, но его конкретное воспроизведение здесь не доказано. Сырые upstream headers/body не собирались, приложение не инструментировалось и логирование не включалось ради повторного запроса.

## Вывод и следующий шаг

Доказано: при нынешнем выходе Coolify динамическое разрешение через выбранный DoH endpoint устраняет DNS-зависимое зависание каталога на точном production image. Не доказано: одного DNS достаточно для исправления production Chat Completions. Основной production менять по результату этого опыта преждевременно.

Qwen2API-5s6 отслеживает оставшийся HTTP 502. Минимальная следующая работа — сделать безопасно видимой фазу/HTTP status/content-type отказа штатного upstream-пути, без credentials/сырого body и без повторов по CAPTCHA. Отдельно потребуется подтверждение принятой Qwen сессии. Восстанавливать постоянный статический CDN IP или включать старые удалённые env-переменные этот результат не обосновывает.

## Завершение и артефакты

Все три новых контейнера остановлены, включая baseline для отмены зависшего upstream-запроса. Прежние lab-контейнеры не запускались. Volume/data files не удалялись. В /root/qwen-prod-doh-diagnostic-20261120/ оставлены защищённые диагностические данные/API keys и безопасные JSON summaries; секретные файлы не скачивались на Windows. Не публиковать содержимое private-keys.json, diagnostic.env или data/data.json.

Финальная проверка production совпала с baseline по Id/Image/StartedAt/RestartCount/Dns/ExtraHosts. StartedAt=2026-11-18T14:07:57.34991102Z, RestartCount=0. Вызовов изменения production приложения, его данных или resolver не было.

Воспроизводимый runner: tools/diagnostics/prod-doh-experiment.py. Проверены синтаксис runner и вложенного resolver, отсутствие встроенных JWT и git diff --check; фактические проверки Docker/DNS/API описаны выше. Runner намеренно отказывается повторно выполнять setup поверх существующего диагностического каталога/контейнеров: перед повтором требуется проверить оставшиеся артефакты, а не удалять их автоматически.

Dolt remote отсутствует; по уточнению пользователя синхронизация не выполнялась. Отчёт и runner сохранены локально, инфраструктурные подробности в публичный origin не отправлялись.
