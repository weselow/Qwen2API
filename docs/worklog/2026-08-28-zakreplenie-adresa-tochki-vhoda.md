# 2026-08-28 — Закрепление адреса точки входа chat.qwen.ai

Беда в трекере: `Qwen2API-bg6`. Попутно заведена `Qwen2API-x1v`.

## Что сделано

Служба научилась соединяться с заданным адресом точки входа, сохраняя имя узла
в приветствии TLS, в проверке сертификата и в заголовке `Host`. Настройка —
две переменные окружения со списками адресов через запятую:
`QWEN_CHAT_ENDPOINT_IPS` для `chat.qwen.ai` и `QWEN_CLI_ENDPOINT_IPS` для
`portal.qwen.ai`. Пусто — поведение прежнее, ничего не меняется.

Если адрес перестал отвечать ошибкой передачи данных, служба берёт следующий из
списка и запоминает его. Переключение врезано в цикл повторов запроса к чату и
в создание сессии.

## Почему так

Имя `chat.qwen.ai` ведёт на службу распределения Alibaba, которая выдаёт адрес
по местоположению спрашивающего. Из России достаётся европейская точка
`8.209.x`: соединение устанавливается, шифрование проходит, а поток данных
умирает. Точка `47.x`, которую получают запросы из-за рубежа, работает
безотказно.

Обычные обходы не годятся. Свой сервер имён стоит в России и получает от Google
тот же нерабочий ответ. Запись в `hosts` бесполезна при работе через прокси:
имя разрешает сам прокси, в туннель уходит `CONNECT chat.qwen.ai:443`.
Подстановка адреса прямо в `QWEN_CHAT_PROXY_URL` ломает проверку сертификата.

Изначальный набросок предлагал менять URL запроса на адрес и вручную выставлять
заголовок `Host`. Чтение кода показало, что так делать не надо: все обращения
уже строятся как `` `${chatBaseUrl}/...` `` и уже проставляют `host`, `origin`,
`referer` по имени. Достаточно подменить адрес назначения **внутри агента
соединения** — и чинятся разом все пути: чат, создание сессии, список моделей,
картинки и видео, загрузка файлов, `getstsToken`.

Реализация опирается на устройство `https-proxy-agent`: строка `CONNECT`
собирается из `opts.host`, а шифрование к узлу поднимается через `tls.connect`
с `servername` из `opts.servername`, причём `host` из параметров вычёркивается.
Значит подмена `{ ...opts, host: адрес, servername: имя }` даёт ровно
`curl --connect-to`. Для соединений без прокси то же достигается своим
разрешением имени (`lookup`) на обычном `https.Agent`.

## Что проверять первым при поломке

1. **Запросы к CLI (`portal.qwen.ai`) пошли не туда.** Единственное место, где
   узел не чатовый, — `src/controllers/cli.chat.js`. Он обязан передавать
   `getCliBaseUrl()` вторым доводом в `getProxyAgent`. Без этого получит
   закрепление адреса чата.
2. **Переключение адреса не действует.** Смотреть ключ кеша агентов в
   `src/utils/proxy-helper.js`: он собран из «прокси + имя узла + адрес». Если
   ключ схлопнется до одного прокси, старый агент продолжит держать соединения
   с нерабочим адресом.
3. **Пошли отказы по сертификату.** Значит адрес в списке не принадлежит Qwen.
   Проверка идёт по имени и намеренно не отключается: `rejectUnauthorized` не
   трогали нигде.
4. **Список адресов устарел.** Alibaba их меняет. Признак — все адреса из
   списка отвечают отказом; в журнале видны переключения по кругу. Лечится
   правкой переменной, перезапуск не обязателен только при живом переключении.

## Как проверялось

Тесты `tests/chat-endpoint-pinning.test.js` (девять штук): поддельный прокси
проверяет строку `CONNECT` и параметры приветствия, отдельно — разрешение имени
без прокси в обеих формах вызова, раздельность кеша, перебор по кругу,
неприкосновенность узла CLI, пустой список. Весь набор — 70 из 70.

## Что осознанно не тронуто

* Интерфейс (`public/`) — настройка только через переменные окружения.
* `src/utils/cli.manager.js` — там `applyProxyToFetchOptions` кладёт `agent` в
  глобальный `fetch`, а тот его игнорирует. Значит прокси в потоке входа CLI не
  работает уже сейчас, и закрепление адреса тоже не подействует. Отдельная
  беда `Qwen2API-x1v`.
* Автоопределение адресов через DNS-over-HTTPS — бесполезно: прокси
  расположены там же, ответ придёт тот же нерабочий.
* Загрузка в хранилище через `ali-oss` — другой узел, агента не получает.

Заодно убрано устаревшее правило «backend не трогать» из `CLAUDE.md` и
`.claude/rules/project-conventions.md`.
