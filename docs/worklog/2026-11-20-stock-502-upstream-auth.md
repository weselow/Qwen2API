# Штатный Qwen2API + DoH: установленная причина HTTP 502

20 ноября 2026, наблюдения 19:19 и 19:21 UTC / 23:19 и 23:21 Europe/Saratov.
Диагностика: Qwen2API-5s6; исправление классификации: Qwen2API-7bs. Основание: предыдущий опыт Qwen2API-0uv.

## Вывод

Конкретный воспроизведённый 502 вызван **отказом авторизации upstream при создании чата**. Qwen отвечает HTTP 200 с JSON success=false и кодом unauthorized, без data.id. Штатный generateChatID возвращает null, а вызывающий код превращает это в HTTP 502 upstream_error с сообщением о невозможности создать/продолжить сессию.

DNS в этом опыте работает через динамический DoH. Транспорт и каталог доступны. Наблюдённый ответ не является HTML-страницей CAPTCHA: content-type application/json, JSON успешно разобран, известных HTML/JSON-маркеров WAF не найдено. Это устанавливает непосредственную причину данного 502; не исключает WAF на других запросах/маршрутах.

## Доказательства

| Проверка | Результат |
|---|---|
| Штатный /v1/models через DoH | HTTP 200, 14 моделей; 0.991 s и 1.122 s |
| Один non-stream в первом наблюдении | HTTP 502 upstream_error, 0.278 s |
| Уточняющее наблюдение после добавления безопасной классификации | HTTP 502 upstream_error, 0.288 s; сообщение совпадает с веткой отсутствующего chat ID |
| Реальный stock POST /api/v2/chats/new | HTTP 200, application/json; success=false; код unauthorized; data.id отсутствует |
| Отправленный Bearer | Присутствует и побайтово совпадает с JWT диагностического аккаунта; проверялось только равенство, значение не выводилось |
| Отправленный token cookie | Присутствует и совпадает с тем же JWT |
| Дополнительный read-only GET /api/v1/auths/ | HTTP 401 JSON с тем же in-memory профилем заголовков; Bearer/cookie совпадают с JWT |
| Проверка WAF | HTML=false; aliyun_waf_, AliyunCaptcha/verification markers и FAIL_SYS_USER_VALIDATE/RGV587 не обнаружены |
| JWT exp | В будущем, около 681356 секунд оставалось при предварительной проверке; claim iat отсутствует |

В первом наблюдении классификатор смотрел только поверхностные поля error/detail и не распознал код вложенного JSON. После расширения на поля code/error_code/message/msg/detail/status получен разрешённый код unauthorized. Это было одно ручное уточняющее наблюдение с той же сессией, без ротации аккаунтов и автоматических повторов. Для обеих проб identity query возвращал 401. Сырые тела ответов не сохранялись; точный произвольный текст ошибки не цитируется.

Будущий exp показывает только то, что локальная проверка срока считает JWT действующим. TokenManager.validateToken в проекте декодирует JWT и сравнивает exp с текущим временем; подпись, отзыв сессии и принятие Qwen не проверяет. Успешный каталог также не доказывает авторизацию: он здесь отвечал при отклонённой сессии.

## Как наблюдался точный image

Приложение запущено из image ID sha256:ba61eb69855445944896f43627ac467456a08e1f0303658785578f7b41cf6794. SHA-256 /usr/local/bin/qwen2api остался 02de782681749b2e509bbbdfdd8651ee6d1c1cb7d81c25bd51015e5472688686, совпадает с production и предыдущим опытом. Образ и бинарник не пересобирались и не патчились; lab-изменения cookies/headers/fingerprint/refresh не применялись.

На одноразовый диагностический запуск добавлен BUN_OPTIONS=--preload=/observer.cjs. Поддержка preload сначала проверена в отдельном контейнере без сети и аккаунтов: preload сработал и завершил процесс с контрольным exit 42. Использована возможность runtime flags для standalone Bun 1.3.14: https://github.com/oven-sh/bun/blob/bun-v1.3.14/docs/bundler/executables.mdx .

Наблюдатель оборачивает node:http/node:https request и наблюдает response, сохраняя обычный native HTTP/TLS путь. Никакого MITM, подмены сертификатов, отключения TLS или изменения URL приложения нет. Наблюдаются реальные ответы запроса stock generateChatID. К response добавлен listener до axios, чтобы прочитать content-encoding до его удаления axios; копия ограниченного тела классифицируется только в памяти и не изменяет исходный поток. Сам preload и дополнительный read-only auth query — явные диагностические отличия от запуска без наблюдателя.

Наблюдатель сохраняет только allowlist endpoint paths, числовые status/counts, фиксированные content-type/error-code категории и булевы признаки. Authorization, Cookie, Set-Cookie, API keys, email, user ID, raw request/response body не сохраняются. Сопоставление идентичности и JWT выполняется в памяти; наружу выходят только true/false. Application logging driver=none, file logs отключены.

## Изоляция и сохранность production

Созданы qwen2api-prod-doh-observed-20261120 (loopback 23215) и qwen2api-prod-doh-observed-verified-20261120 (loopback 23216), запускались последовательно. Использован прежний DNS sidecar qwen2api-prod-doh-resolver-20261120; основной production не трогался. Прежние baseline/lab приложения не запускались.

Взята та же диагностическая копия одного аккаунта из предыдущего опыта. Password/proxy пусты, CLI выключен, chatRetryCount=0. Новые production-аккаунты/credentials не извлекались и не перебирались. Токен не обновлялся, программный вход и решение CAPTCHA не выполнялись. AutoRefresh=false установлен через штатный API; шестичасовой startup interval не успевал сработать до остановки.

Оба наблюдаемых приложения и DNS sidecar остановлены в finally. Secret data/env остались только на сервере в защищённых каталогах /root/qwen-prod-doh-502-20261120 и /root/qwen-prod-doh-502-verified-20261120; сохранённые summaries содержат только безопасные поля. Backup/volumes не удалялись. Основной e7198260faec всё время работал на прежнем image, StartedAt=2026-11-18T14:07:57.34991102Z, RestartCount=0; проверка Id/Image/StartedAt/RestartCount/Dns/ExtraHosts совпала с baseline.

## Что осталось неизвестным и что делать дальше

Установлен отказ авторизации **для выбранной диагностической сессии на direct/DoH маршруте**. Причину её непринятия сервер не раскрывает в сохранённых категориях. Возможны отзыв/устаревание сессии, изменение серверных условий либо привязка к контексту сессии/выходу. Исходный аккаунт имел HTTP-прокси, который убран только в диагностической копии; работоспособность этого же JWT через исходный прокси здесь не проверялась. Нельзя утверждать, что все шесть JWT с будущим exp в production непригодны или что исправление DNS достаточно для авторизации.

Следующий функциональный контроль — сессия, принятие которой подтверждено самим Qwen, сначала read-only identity, затем одна генерация в изолированном штатном image. При необходимости отдельно сравнить тот же JWT через исходный proxy/direct, не меняя production. Этот аудит не выполняет вход/refresh и не подбирает заголовки для обхода отказа.

В коде требуется отдельно распознавать JSON success=false/code unauthorized до извлечения data.id и возвращать безопасную категорию upstream authentication failure. Это другой случай, чем Qwen2API-2ij (HTTP 200 + HTML CAPTCHA). Код приложения в текущей работе не менялся.

Локальные инструменты: tools/diagnostics/upstream-safe-observer.cjs и tools/diagnostics/diagnose-stock-502.py. Проверки: node --check, Python AST, офлайн preload probe, реальные stock upstream/API наблюдения, git diff --check, финальная проверка остановки/production invariants. Dolt remote отсутствует; инфраструктурный отчёт и инструменты в публичный origin не отправлялись.
