# Та же сессия: прямой DoH и исходный HTTP proxy

21 ноября 2026, Europe/Saratov. Пробы 20 ноября 20:01–20:07 UTC и 21:15 UTC соответствуют 00:01–00:07 и 01:15 Саратов 21 ноября. Задача Qwen2API-lc1.

## Итог

Прямой маршрут с динамическим DoH стабильно возвращает HTTP 401 на read-only GET /api/v1/auths/ с прежним диагностическим JWT. Через исходный HTTP-прокси с этой же сессией HTTP-ответ получить не удалось: CONNECT 200 и проверенный TLSv1.3 устанавливаются, затем происходит timeout до HTTP response headers. Увеличение ожидания с 10 до 30 секунд не помогло.

Поэтому проверка не доказывает ни принятие, ни отклонение JWT через исходный прокси. Нельзя заключить, что unauthorized вызван только сменой выхода, или что возвращение к прежней proxy-конфигурации исправит сессию. Пользователь решил прекратить тесты этого прокси и впоследствии попробовать другие.

## Условия и сравнение

Диагностический аккаунт однозначно сопоставлен с production по совпадению email и самого JWT (ровно одно совпадение). Извлечена только его исходная proxy-конфигурация для защищённой диагностической копии. Это http://eu.proxy.rucaptcha.com:2334; username/password не выводились и в Git не помещались. Пароль Qwen не копировался. На старте заключительной пробы до JWT exp оставалось около 674214 секунд.

Штатный image ID sha256:ba61eb69855445944896f43627ac467456a08e1f0303658785578f7b41cf6794, SHA-256 /usr/local/bin/qwen2api = 02de782681749b2e509bbbdfdd8651ee6d1c1cb7d81c25bd51015e5472688686. Одноразовый preload получал текущий stock header profile из каталожного запроса. Профиль передавался только один раз через защищённый локальный endpoint в память controller, затем через stdin отдельному Python helper-контейнеру. Raw headers/cookies/JWT не сохранялись в файлы/логи и не выводились.

Внутри пары одинаковы JWT, cookie, UA/fingerprint profile, целевой путь и TLS-клиент. В независимом Python-контроле для обоих маршрутов одинаково нормализованы Accept=application/json, Accept-Encoding=gzip и Connection=close, удалены заголовки длины/transfer-encoding для GET. Два маршрута используют одинаковый Python SSL/HTTP клиент; основной Qwen2API не менялся.

У штатного getLatestModels при первом upstream-сбое возвращается [], поэтому HTTP 200 с 0 моделей не является успешным запросом каталога. Allowlist-наблюдатель logger не распознал у быстрого сбоя image ни HTTP status, ни 407, ни известный headers/body/socket timeout; точная причина этого быстрого сбоя не установлена, произвольный текст ошибки не сохранялся. Не считать её автоматически той же причиной, что timeout независимых клиентов.

Предварительные Bun raw-socket контроли тоже зависали после TLS. Из-за возможных различий работы обёрнутого socket результат независимо проверен Python helper. HTTP parser был уточнён для завершения по Content-Length/chunked, а в Python HTTP status фиксировался сразу после headers до чтения body. Независимые проверки подтвердили timeout именно до response headers, не ожидание конца уже полученного тела.

Запросов генерации, создания чата, входа, refresh, ротации аккаунтов или смены proxy credentials не выполнялось. После наблюдения отказа не предпринималось решения CAPTCHA/WAF. Через прокси не получено тела HTTP-ответа, поэтому классифицировать там WAF или auth-отказ нельзя. В direct HTTP 401 известных WAF-маркеров не обнаружено.

## Ограничения и завершение

Исходная proxy-конфигурация не гарантирует тот же исторический публичный IP: фактический egress IP во время выдачи JWT неизвестен, прокси-сервис может менять выход. Здесь сравнивались маршруты через сохранённую конфигурацию и direct; привязка к конкретному историческому IP не установлена.

Тесты этого proxy прекращены по просьбе пользователя. Неразрешённые транспортные вопросы и быстрый сбой stock proxy catalog остаются в Qwen2API-o7u; нужна рабочая proxy-маршрутизация для полноценного auth-сравнения. Последующее исправление JSON unauthorized по-прежнему Qwen2API-7bs.

Все созданные приложения/helper/DNS контейнеры остановлены либо одноразовые helpers удалены Docker после выхода. Прежний production e7198260faec не перезапускался: StartedAt=2026-11-18T14:07:57.34991102Z, RestartCount=0, image/DNS/ExtraHosts совпадали с baseline после каждого опыта. Секреты остались только в защищённых диагностических каталогах /root; volumes не удалялись.

Локально сохранены session-profile-once.cjs, session-egress-client.py, compare-session-egress-client.py и stock-proxy-error-observer.cjs. Проверены Python AST, node --check, credential-pattern scan и git diff --check. Отчёт и инструменты не отправлялись в публичный origin; Dolt remote отсутствует.
